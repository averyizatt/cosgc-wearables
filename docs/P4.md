# ESP32-P4 port (Waveshare ESP32-P4-Pico)

**Status (2026-11-01): runs on a real board.** The 24-layer 19 M model, our most accurate (25.1 % WER on TORGO test with the language model, shipped model 37.4 %), streams at
**0.602 times real time on two cores** (0.967 on one) and the shipped 13 M model at 0.748 on one core (S3: 1.54), all with transcripts
word-for-word the same as the host engine on four clips. All four vector kernels pass their self-test, and the codec answers.
**Not tested yet:** recognizing a person speaking at the board, a screen and a button. Full record: [EXPERIMENTS.md](EXPERIMENTS.md), E9, E9b and E10;
logs in [`results/`](results/).

## The board

ESP32-P4NRW32: two RISC-V cores at 400 MHz (measured), 32 MB PSRAM in the package (hex, 200 MHz), 32 MB flash (GigaDevice
c8/4019), an ES8311 audio codec with an onboard microphone, an NS4150B speaker amplifier, microSD, MIPI display and camera
connectors, BOOT and RST buttons. **No Wi-Fi or Bluetooth** (the P4 has no radio; boards that have one carry an ESP32-C6 for it).
Source: [Waveshare wiki](https://www.waveshare.com/wiki/ESP32-P4-Pico).

Our chip is revision v3.2. Its USB port is a CH343 serial bridge to UART0 (it shows up as a COM port), not the chip's USB-Serial/JTAG,
so the console and the device API use UART0. The codec answers with chip id 0x8311 at the pins below, so the I2C wiring matches.

| Function | GPIO |
|---|---|
| I2C SDA / SCL (codec, address 0x18; also free for an OLED at 0x3C) | 7 / 8 |
| I2S MCLK / SCLK / LRCK / ASDOUT (mic data to the chip) / DSDIN | 13 / 12 / 10 / 11 / 9 |
| Speaker amplifier enable (we drive it low: no sound out) | 53 |
| SD card CLK, CMD, D0..D3 | 43, 44, 39..42 |

There is no user button or LED on the board. The pins are in [`esp32/firmware/sdkconfig.p4`](../esp32/firmware/sdkconfig.p4).

**Adding a screen and a button.** Screen: an SSD1306 128x64 I2C OLED, address 0x3C: VCC to 3V3, GND to GND, SDA to GPIO7, SCL to GPIO8 (the codec's bus, shared on
purpose). The firmware already looks for it and logs a warning if it is missing. Button: one side to GND, the other to a free GPIO marked on the header (internal pull-up), then
set `CONFIG_TASR_PTT_GPIO` in `sdkconfig.p4` and rebuild. Avoid 7-13 (codec, I2C), 37-38 (serial console), 39-44 (SD card) and 53 (amplifier). From memory of the P4's pinout, not checked
for this board, also avoid 34-36 (boot pins) and 24-27 (USB). Until a button is set, the voice-activity detector starts and ends utterances, or a client can use the `talk` command of the device API.

### The vector kernels

The S3 and the P4 both have a 128-bit "PIE" vector unit that multiplies 16 int8 pairs per instruction, but the instruction
names, the accumulator names and the loop mechanism differ (`ee.vmulas.s8.accx` on the S3, `esp.vmulas.s8.xacc` on the P4;
the S3's zero-overhead `loopnez` becomes a counter and a branch). We ported the kernels that carry the work:

| Kernel | What | Ported how |
|---|---|---|
| `tasr_dot_rows_s8` | int8 dot products (attention, head) | S3 schedule, XACC accumulator |
| `tasr_dot48_rows` | 48-byte attention dot | same |
| `tasr_gemm_s8_xr` | int8 rows GEMM | built on `tasr_dot_rows_s8` (simple, correct, not the S3's register-blocked version) |
| `tasr_gemm_blk16` | int4-weight GEMM (most layers) | QACC (`esp.vsmulas.s8.qacc`), the S3 schedule |
| `tasr_unpack_s4` | int4 to int8 | 4 bytes at a time in plain C ("SWAR"); also used by the host and is bit-identical to the old loop (tested on 2,000 random blocks) |

**Not ported**: the S3's broadcast "x-stationary" kernel with 6 vectors held in registers (the P4 uses the generic path
instead). The two-core spin-wait mode works as on the S3 (`oido_p4_2c`, `oido_p4_bench_2c`); core 1 never sleeps in it.
The P4 keeps the language model in int8, as the host evaluations do; the S3's int4 version exists for its slower PSRAM.

**Safety net.** A PIE kernel that is wrong is worse than a slow one. So at boot `tasr_p4_selftest()` compares every vector
kernel with a plain-C reference on random data and prints `P4SELFTEST` lines. If one differs, the vector path is switched off and
the engine runs on C (slower, correct). What the board settled:

1. **QACC readout:** layout 1. The self-test still tries both layouts at each boot.
2. **Instruction encoding:** this chip uses IDF's default `-march=rv32imafc_zicsr_zifencei_xesploop_xespv`. Do **not** add
   `xesppie`: the same mnemonics assemble to other opcodes (`esp.zero.xacc` is `0x1b`, not `0x5b`) and the first one crashes
   with a meaningless cause such as `MCAUSE 0x1f`. To check an object file: `riscv32-esp-elf-readelf -A kernels.c.o`.
3. **Registers:** only `a0`..`a5` are accepted for vector addresses, so the kernels pin their pointers to `a3`..`a5`.

If the board crashes before the `P4SELFTEST` lines appear, set `CONFIG_TASR_P4_PIE=n` in `sdkconfig.p4`. The self-test covers
the kernels only: it stayed green while the model in flash was damaged, so also compare transcripts with `tasr_cli --stream`.

## First build and bring-up

PlatformIO's own `espressif32` platform has no ESP32-P4 support, so the `oido_p4` environment uses the **pioarduino** fork of the
platform (ESP-IDF 5.5). The first build downloads it from GitHub. Everything else (S3 environments) is unchanged.

```
subst P: "C:\path\to\IEEE CLub"        # the project path must not contain spaces
cd P:\cosgc-wearables
pio run -e oido_p4                       # builds
python esp32/tools/flash_p4.py COM3 --env oido_p4_2c                   # flashes everything, about 5 minutes for a 14 MB model
python esp32/tools/flash_p4.py COM3 --env oido_p4_2c --only app        # after a code change: seconds
python esp32/tools/flash_p4.py COM3 --env oido_p4_2c --only model --model big2_q121.tnm     # another model, no rebuild: 8 minutes
pio device monitor
```

`pio run -t upload` still works for the app and language model, but skips the model, which it cannot write across 16 MB.

Things that bite on this board:

- **Flashing uses the ROM loader** (`--no-stub`, added by `esp32/firmware/pio_nostub.py`). esptool's stub fails here at every
  baud rate ("Invalid head of packet (0x61)", "The chip stopped responding"). The ROM loader works at 921600 and at 2 Mbaud.
- **Do not edit `platformio.ini` during a build or flash while VS Code is open:** the PlatformIO extension then runs
  `project init`, which rewrites the shared package folder. Wait for it to finish; the next build reinstalls the tools (about 17 minutes
  in all). Do not kill PlatformIO during a tool install: it removes the toolchain first.
- **After editing a component's `CMakeLists.txt`,** touch `esp32/firmware/main/CMakeLists.txt`. PlatformIO only re-reads CMake
  when the top-level one changes, and otherwise silently keeps the old compile flags.

### Flash above 16 MB

The ROM loader and the cache use 3-byte addresses, so anything above 16 MB wraps around (`0x1A10000` lands on `0xA10000`), and hash
checks still pass because the read-back wraps the same way. Our first layout overwrote part of the model like that. What we do now:

- **Writing:** `esp32/tools/flash_p4.py` selects the flash bank through the chip's Extended Address Register (C5h / C8h), splits images at the
  boundary, and verifies every image again after the last write. It always leaves bank 0 selected, because resetting the board does not
  reset the flash chip. If a run dies with bank 1 selected and the board will not boot, power-cycle it or rerun the tool.
- **Reading:** the app, language model and clips stay below 16 MB, where they are memory-mapped. The model may cross it: at boot
  `read_partition_to_psram()` copies it to PSRAM through the flash driver, which uses 4-byte commands (about 11 MB/s: 1.3 s for 13 M, 1.9 s
  for 19 M). ESP-IDF's experimental `CONFIG_BOOTLOADER_CACHE_32BIT_ADDR_QUAD_FLASH` is not needed.
- **Layout (`partitions_p4_32.csv`):** 1 MB app, 4 MB LM, 1 MB clips, 24 MB model, about 1.9 MB free at the end.

Check, in this order (each takes minutes, and each one tells you what to fix next):

1. **Chip revision.** `esptool chip_id`. The board file assumes a current chip (revision 3.x). If it reports an older "ES" chip,
   change `CONFIG_ESP32P4_REV_MIN_*` (or use the pioarduino `esp32-p4` ES board).
2. **Boots, prints `P4SELFTEST` lines.** All `PASS` is the goal. A `FAIL` is not a crash: the engine continues on C.
3. **Codec.** The log line `chip id 0x8311` confirms the I2C address and pins. If the ID is wrong, the I2C pins or address are.
4. **Microphone level.** With a USB client (`esp32/tools/oido_client.py`) request `level` and talk at the board. The codec gain is
   `CONFIG_TASR_CODEC_MIC_GAIN` (steps of 6 dB, default 4 = 24 dB). Compare with the level-bar marker (-55 dBFS) from the S3 notes.
   The board's microphone sits next to a speaker amplifier on a board you hold in a hand, so expect more noise than the INMP441 on
   a stalk. Run the quiet-speech and noise checks again; do not reuse the S3 numbers.
5. **Speed.** Flash `oido_p4_bench` and read the `TOTAL` line. Measured on one core (S3: 1.54); a run with the plain-C kernels takes
   5.25, so the vector kernels give about 6.9 times:

   | | wall RTF | final text after speech ends | min free PSRAM |
   |---|---|---|---|
   | shipped, 13 M, 16 layers, one core | **0.748** | at most 822 ms (before the model moved to PSRAM) | 14.4 MB |
   | big2, 19 M, 24 layers, one core, int4 LM | **0.967** | at most 1120 ms | 6.5 MB |
   | big2, two cores, int8 LM | **0.602** | at most 745 ms | 6.0 MB |

## What the extra memory can buy

The S3 has 8 MB PSRAM and a 16 MB flash; the P4 board has 32 MB of each. Where that goes today and where it could go:

| | S3 (today) | P4 | Notes |
|---|---|---|---|
| Model weights (14 MB, int8) | read from flash through a small cache, hot part copied to PSRAM (1.4 MB) | the whole model in PSRAM, read at boot, plus the LM | no flash cache misses: RTF 0.759 → 0.748 |
| Audio ring buffer | 32 s (about 1 MB) | minutes (5 minutes = 9.6 MB) | absorbs a recognizer that runs slower than real time |
| Several models at once | one | e.g. streaming English + accurate English + Spanish (3 x 14 MB = 42 MB of flash: **does not fit** with the LM; two do) | flash is the limit, not PSRAM |
| Partition layout | 1.4 MB LM, 14 MB model | `partitions_p4_32.csv`: 24 MB model, 4 MB LM, 1 MB clips | see "Flash above 16 MB" |

What to *do* with the room is a compute question as much as a memory question. Measurements we have:

**Upstream LibriSpeech results** (from `results/*.json`, beam search with the pruned-decoder LM; WER %, test-clean / test-other):

| Model | Mode | clean | other |
|---|---|---|---|
| `oido_stream` (shipped here) | streaming, 1.28 s chunks | 4.86 | 11.03 |
| `oido_stream` | streaming, 0.64 s chunks | 6.14 | 13.23 |
| `oido_stream` | full context (whole utterance) | 3.43 | 7.78 |
| `nemo4` (int4) | full context | 3.78 | 8.43 |
| `nemo8` (int8) | full context | 3.33 | 7.15 |

So the biggest accuracy lever is **not** a bigger beam or more context memory: it is running the **full-context model** (`nemo8`
or `oido_stream` in full-context mode), which cuts errors by about a third, at the price of a longer wait after releasing the
button (the whole utterance is computed then, not just the last chunk). On the S3 that wait is seconds; on the P4 it depends on
the speed measured above. With a push-to-talk button this trade is a user setting, not a hardware limit.

**Our host runs** (four bench clips, 65 words; too few to rank settings by accuracy, so read only the timing column):

| Setting | WER | host CPU (4 clips) |
|---|---|---|
| streaming, beam 4 (shipped) | 3.1 % | 5.5 s |
| streaming, no language model | 3.1 % | 5.3 s |
| streaming, beam 1 / 16 / 32 | 3.1 % each | 5.4 / 6.2 / 6.3 s |
| streaming, left context 1 / 4 / 16 chunks | 3.1 % each | 5.5 / 5.6 / 5.5 s |
| streaming, chunk 16 / 64 | 3.1 % each | 5.6 / 5.5 s |
| `nemo8` (full context) | 4.6 % (3 of 65 words) | 5.5 s |
| `nemo4` | 3.1 % | 4.6 s |

Reading it: **beam width costs about 15 % more compute for 16 to 32, and bought nothing on these clips**; a larger left
context did not change the run time on short clips (it matters for long utterances); and on 65 words one word is 1.5 %, so
no model difference here is meaningful. A fair comparison needs a larger test set: LibriSpeech (not on this PC) or, better, recordings of the people this is
for (see [ATYPICAL_SPEECH.md](ATYPICAL_SPEECH.md)). The scripts to run the sweep on a bigger set are `esp32/host/eval_engine.py` and `tasr_cli`.

**Recommendation.** For the P4, in order of expected value: (1) test the 24-layer model with a person speaking; (2) offer the
full-context model for push-to-talk if the measured wait after release is under about 2 seconds; (3) use the memory for a long
audio ring and weights entirely in PSRAM; (4) spend the rest of the flash on a model fine-tuned for the target speakers rather than a
second general model.
